# ТЗ для Codex: персональный productivity-трекер с растущим котёнком

## 0. Главная идея проекта

Нужно создать **полностью самостоятельный визуально проект**, а не вариацию/редизайн чужого Focus Tool.

Это персональный веб-трекер для ежедневных дел и фокус-сессий. Его эмоциональный центр — **цветной виртуальный котёнок**, который постепенно растёт благодаря действиям пользователя.

Основная метафора:

> Я делаю небольшие реальные дела → мой котёнок растёт → я вижу накопленный прогресс → вместе с ним расту и я.

Сайт должен ощущаться как **красивый, уютный, дорогой digital-продукт**, которым хочется пользоваться каждый день. Это не корпоративный таск-менеджер и не детская игра. Нужен баланс: **cozy + premium + modern + playful**.

---

# 1. КРИТИЧЕСКИЕ ПРАВИЛА ДЛЯ CODEX

## 1.1. Не упрощать визуал

**НЕЛЬЗЯ** заменять полноценный визуальный дизайн:
- эмодзи;
- стандартными Unicode-символами;
- случайными иконками вместо иллюстраций;
- примитивными кружочками/квадратиками;
- CSS-рисунком кота;
- generic placeholder art;
- одной абстрактной SVG-мордочкой;
- картинками-заглушками.

Если для красивого результата нужны изображения — **сгенерируй изображения**.

В приоритете визуальное качество. Не делать «минимально рабочую демку». Нужно сделать **полноценный polished интерфейс**, который уже на первом экране вызывает «вау».

## 1.2. Использовать image generation

Если в текущей среде Codex доступен **image generation skill / GPT Image**, ОБЯЗАТЕЛЬНО используй его для создания оригинальных ассетов проекта.

Не жди отдельной просьбы пользователя.

Если image generation в текущем окружении недоступен:
1. **не заменяй картинки эмодзи или примитивными CSS-иконками**;
2. создай полноценную систему путей/компонентов под будущие ассеты;
3. явно сообщи, каких изображений не хватает;
4. оставь проект визуально аккуратным, но не маскируй отсутствие арта дешёвыми заменами.

## 1.3. Котёнок — главный визуальный герой

Котёнок должен выглядеть как **настоящий оригинальный игровой персонаж**, а не как системная иконка.

Требования:
- цветной;
- выразительный;
- милый, но не инфантильный;
- узнаваемый силуэт;
- визуально одинаковый персонаж на всех стадиях;
- качественный digital illustration / polished game asset;
- прозрачный фон у основных PNG/WebP ассетов;
- мягкий объём, приятный свет, аккуратные детали;
- без текста внутри самих изображений.

## 1.4. Проект должен быть визуально самостоятельным

Не копировать:
- зелёную палитру референса;
- сад/горшок;
- пейзаж с круглым Pomodoro;
- карточную композицию чужого проекта;
- конкретные размеры/расположение блоков;
- его фирменные элементы.

Функциональные идеи можно использовать, но визуальная система и композиция должны быть своими.

# 2. Визуальная концепция

## 2.1. Общий стиль

Направление:

**cozy premium productivity app + virtual pet**

Ассоциации:
- мягкий вечерний свет;
- уютное личное digital-пространство;
- хороший современный интерфейс;
- немного игровой магии;
- чистая типографика;
- цвет, глубина и объём;
- никаких «детсадовских» элементов.

Избегать:
- стерильного SaaS-интерфейса;
- кислотных цветов;
- слишком большого количества белых одинаковых карточек;
- чрезмерной пустоты;
- неонового gaming UI;
- пиксельного ретро-тамагочи;
- визуала в стиле мобильной игры для маленьких детей.

## 2.2. Палитра

Сделать оригинальную палитру, не похожую на зелёный референс.

Базовое направление:
- тёплый кремовый / very light warm beige background;
- глубокий графитовый текст;
- основный акцент: приглушённый сливовый / dusty violet / berry;
- вторичный акцент: мягкий небесно-голубой;
- немного тёплого персикового/абрикосового для живости;
- у категорий задач — собственные спокойные цвета.

Не превращать всё в пастельную «зефирную» массу. Нужен хороший контраст.

## 2.3. Глубина

Использовать:
- многослойные мягкие тени;
- subtle inner highlights;
- тонкие границы;
- аккуратные градиенты;
- небольшую текстуру/зерно на фоновых областях;
- живые hover/pressed states;
- плавные transitions;
- micro-interactions.

Не использовать:
- тяжёлые чёрные drop shadows;
- glassmorphism ради glassmorphism;
- слишком много blur.

## 2.4. Адаптивность

Главный приоритет — desktop.

Но обязательно:
- корректная работа на ноутбуке;
- tablet layout;
- mobile layout без горизонтального скролла;
- котёнок и timer не должны ломать сетку.

# 3. Структура главного экрана

Нужен один цельный dashboard, а не десять отдельных страниц.

На desktop он должен содержать:

1. Header
2. Focus timer + Brown Noise
3. Блок котёнка
4. Календарь
5. Большой список дел
6. Короткую статистику текущего дня

Композицию придумай самостоятельно так, чтобы интерфейс выглядел **как законченный дизайнерский продукт**, а не как Bootstrap-grid из одинаковых карточек.

Котёнок должен быть заметным и эмоционально центральным, но не отнимать половину экрана у списка дел.

---

# 4. Header

Показывать:
- название проекта;
- текущую дату;
- текущее время.

Можно использовать короткое рабочее название вроде `Mellow`, `Grow`, `Nook`, `Pawgress`, но **не зашивать окончательный бренд слишком жёстко**: вынести название в одну константу, чтобы его легко заменить.

Не использовать название `Focus Tool`.

---

# 5. Список дел

Это один из основных блоков.

## 5.1. Фильтры состояния

Обязательно:

- **Все**
- **Активные**
- **Готовые**

Переключение без перезагрузки.

## 5.2. Создание задачи

Для новой задачи пользователь вводит **только текст**.

Не спрашивать:
- время;
- длительность;
- дедлайн;
- приоритет;
- проект;
- дату выполнения.

Задача должна создаваться быстро.

## 5.3. Теги

У каждой задачи может быть один из постоянных тегов:

- **Работа**
- **Паблик**
- **Личное**

Тег должен выбираться **одним кликом по красивым chip-кнопкам**.

Дополнительно должен быть фильтр по тегам.

Теги не должны выглядеть как эмодзи.

Для каждого тега создать собственный цветовой стиль, гармоничный общей палитре.

## 5.4. Действия с задачей

Нужно:
- отметить выполненной;
- вернуть из выполненных;
- удалить;
- изменить текст;
- изменить тег.

Выполненная задача визуально спокойнее, но остаётся читаемой.

## 5.5. Важное ограничение

**НЕ связывать задачу с таймером.**

Пользователь не должен:
- выбирать задачу перед запуском Pomodoro;
- указывать, сколько она займёт;
- назначать задаче focus session.

Timer и todo-лист — связанные статистикой части одного dashboard, но пользователь запускает timer вручную независимо от конкретной задачи.

# 6. Focus Timer

Timer — отдельный инструмент.

## 6.1. Режимы

Предусмотреть:
- 25 минут;
- 45 минут;
- 60 минут;
- пользовательское значение.

Можно сохранить классические быстрые переключатели:
- Focus;
- Short break;
- Long break;
- Custom,

но визуально и функционально не копировать референс.

Если это усложняет интерфейс, предпочтительнее:
- 25;
- 45;
- 60;
- Свой.

## 6.2. Управление

Нужно:
- Start;
- Pause / Resume;
- Reset;
- корректный countdown;
- завершение сессии;
- визуально приятный completion state.

Timer должен продолжать корректно считать время, даже если вкладка была неактивной. Не полагаться только на `setInterval` decrement; хранить target timestamp / elapsed state.

## 6.3. Завершённая focus session

Focus session считается завершённой, только если timer дошёл до конца.

После завершения:
- увеличить число сессий текущего дня;
- добавить фактическое focus-время в дневную статистику;
- дать котёнку growth XP;
- показать красивую короткую реакцию котёнка.

Если timer был reset до завершения — сессию не засчитывать.

---

# 7. Brown Noise

Пользователь хочет вручную включать brown noise и работать.

## 7.1. Это отдельный контрол

Noise **не обязан автоматически запускаться вместе с timer**.

Нужно:
- Play / Pause;
- громкость;
- mute;
- loop;
- отображение состояния.

## 7.2. Аудиофайл

Сделать конфиг/константу для пути, например:

`/audio/brown-noise.mp3`

Если файла пока нет:
- проект не должен падать;
- показать понятное состояние unavailable;
- не использовать сторонний URL без явной необходимости.

Предусмотреть место, куда пользователь сможет положить свой MP3.

## 7.3. Поведение браузера

Учесть autoplay restrictions: звук запускается только после явного действия пользователя.

---

# 8. Календарь

Нужен аккуратный **месячный календарь**, который реально отображает историю прогресса.

## 8.1. Возможности

- текущий месяц;
- переход назад/вперёд;
- выделение сегодняшнего дня;
- отображение дней недели;
- данные по каждому дню.

## 8.2. Индикаторы

На днях ненавязчиво показывать интенсивность/наличие активности.

Можно использовать:
- маленькие точки;
- несколько уровней насыщенности;
- маленькое кольцо прогресса;
- другой красивый ненавязчивый индикатор.

Не перегружать клетку числами.

## 8.3. При клике на день

Открыть небольшой popover/modal/detail panel:

- дата;
- сколько задач выполнено;
- сколько focus sessions;
- сколько всего focus-времени.

Если удобно архитектурно — также показать названия выполненных в этот день задач.

---

# 9. Виртуальный питомец: котёнок

Это **не отдельная мини-игра, а эмоциональное сердце productivity tracker**.

## 9.1. Общий принцип

Котёнок растёт благодаря:
- выполненным задачам;
- завершённым focus sessions.

Никаких наказаний за отсутствие активности.

Котёнок:
- не умирает;
- не болеет из-за пропусков;
- не теряет уровни;
- не вызывает чувство вины.

Если пользователь ничего не делает несколько дней, котёнок просто остаётся на своей стадии.

## 9.2. Имя

При первом запуске:
- предложить дать котёнку имя;
- дать красивый небольшой onboarding;
- разрешить переименовать позже.

Не делать длинную регистрацию.

## 9.3. Стадии роста

Сделать **5 визуально отличающихся стадий одного и того же персонажа**:

1. **Tiny kitten** — совсем маленький котёнок;
2. **Little explorer** — чуть подрос, любопытный;
3. **Growing kitten** — заметно взрослее;
4. **Young cat** — почти взрослый;
5. **Companion cat** — финальная взрослая форма.

Это должен быть **тот же самый кот**, с тем же окрасом, глазами, формой ушей и ключевыми чертами.

Каждая стадия должна ощущаться как реальный рост, а не просто масштабирование одного PNG.

## 9.4. Эмоциональные состояния

Минимум:
- neutral / calm;
- happy;
- sleepy.

Опционально:
- excited при level-up.

Состояния не должны требовать отдельной сложной системы здоровья.

## 9.5. Growth XP

Предложенная простая система:

- выполненная задача: `+10 XP`;
- завершённая 25-мин focus session: `+15 XP`;
- для другого времени focus начислять пропорционально фактическим минутам с разумным cap;
- level-up/stage-up происходит по общему накопленному XP.

Порог стадий вынести в конфиг, например:

- Stage 1: 0 XP
- Stage 2: 100 XP
- Stage 3: 300 XP
- Stage 4: 650 XP
- Stage 5: 1100 XP

Не показывать пользователю сложную математику.

Показывать:
- текущую стадию;
- красивый progress bar «до следующего роста»;
- короткую фразу о прогрессе.

## 9.6. Реакции

После действий котёнок должен кратко реагировать.

Примеры поведения:
- task complete → happy animation;
- completed focus → happy/excited animation;
- stage up → отдельная celebratory animation + эффект;
- idle → subtle breathing / tail / blink animation.

**Не использовать emoji bubble как основное визуальное решение.**

Можно использовать короткий текстовый bubble:
- «Мур, ещё одно дело готово!»
- «Мы хорошо поработали.»
- «Кажется, я подрос!»

Но текст должен быть необязательным и не надоедать.

## 9.7. Никаких ручных обязательств ухода в MVP

В первой версии НЕ добавлять:
- голод;
- кормление по расписанию;
- туалет;
- болезни;
- сон по часам;
- смерть;
- наказания;
- обязательное поглаживание;
- валюту;
- магазин;
- одежду;
- десятки предметов.

Сначала главное: **реальные дела выращивают котёнка**.

# 10. АРТ-ПАК ДЛЯ КОТЁНКА — ОБЯЗАТЕЛЬНО СГЕНЕРИРОВАТЬ

Если доступен image generation skill, создай согласованный набор ассетов.

## 10.1. Сначала создай character reference sheet

Сгенерируй **один мастер-референс персонажа**:
- полный вид котёнка;
- фронт / 3/4;
- палитра окраса;
- цвет глаз;
- форма ушей;
- хвост;
- характерные пятна;
- выражение морды;
- краткая визуальная эволюция всех 5 стадий.

Сохрани его как внутренний style reference для последующих генераций.

Цель — не допустить, чтобы на каждой стадии появлялся «другой кот».

## 10.2. Затем создай игровые ассеты

Для каждой из 5 стадий нужны изображения как минимум:

- calm/neutral;
- happy;
- sleepy.

То есть целевой набор: **15 согласованных character assets**.

Если image generation позволяет удобнее сохранить согласованность через sprite sheet — сначала создай sheet, затем программно нарежь его на отдельные прозрачные PNG/WebP.

## 10.3. Формат

Предпочтительно:
- PNG или WebP;
- прозрачный фон;
- квадратный canvas;
- достаточное разрешение для Retina;
- единый масштаб персонажа;
- одинаковая точка опоры, чтобы при переключении стадий кот не «прыгал».

## 10.4. Стиль персонажа

Промпт-направление:

> A charming original colored kitten character for a premium cozy productivity web app. Soft polished digital illustration, expressive eyes, warm personality, elegant stylization, rounded but believable anatomy, subtle painterly texture, beautiful soft lighting, modern game asset quality, not pixel art, not emoji, not flat icon, not generic vector mascot, not childish clipart. Transparent background. Consistent character design across growth stages.

Можно улучшить промпт самостоятельно, но сохранить этот художественный вектор.

## 10.5. Критерий качества

Не принимай первый результат автоматически.

Проверь:
- одинаков ли окрас;
- одинаковы ли глаза;
- совпадают ли ключевые черты;
- нет ли лишних лап/хвостов;
- прозрачный ли фон;
- хорошо ли выглядит на размере dashboard;
- не выглядит ли как стикер из мессенджера.

Если результат слабый — **перегенерируй**, а не внедряй плохой ассет.

# 11. Дополнительный декоративный арт

Чтобы сайт выглядел «вау», можно сгенерировать несколько **очень сдержанных** дополнительных ассетов:

- subtle decorative paw-pattern / abstract texture;
- мягкая иллюстративная подложка за зоной питомца;
- маленькие particles/sparkles для stage-up;
- декоративная лежанка/подушка/коврик под котёнком.

Но:
- не превращать страницу в иллюстрированный детский альбом;
- не делать каждую кнопку картинкой;
- не перегружать background.

Основной UI остаётся интерфейсом, а арт усиливает его.

# 12. Анимации

Использовать CSS / Framer Motion (если уместно и уже есть в stack).

Нужны:

### Котёнок
- subtle breathing;
- blink;
- небольшой tail/body motion;
- happy bounce;
- sleepy float/breath;
- stage-up animation.

### UI
- hover;
- press;
- task completion;
- progress update;
- tab switching;
- modal/popover;
- timer completion.

Все анимации:
- плавные;
- короткие;
- не раздражающие;
- поддерживать `prefers-reduced-motion`.

Не использовать бесконечные flashy-анимации.

---

# 13. Дневная статистика

Показывать только понятные метрики:

- выполнено задач сегодня;
- focus-время сегодня;
- завершено focus sessions сегодня.

Не делать абстрактную «эффективность 73%».

Можно показать одну progress line относительно мягкой дневной цели, но не делать её обязательной.

---

# 14. Хранение данных

Для первой версии использовать `localStorage`.

Сохранять:

## Settings
- название/имя котёнка;
- выбранный timer preset;
- volume brown noise.

## Tasks
- id;
- text;
- tag;
- completed;
- createdAt;
- completedAt.

## Focus history
- id;
- startedAt;
- completedAt;
- durationMinutes.

## Pet
- name;
- totalXp;
- currentStage;
- optional temporary mood.

## Calendar/history
Можно вычислять из tasks + focus history, не дублировать без необходимости.

Добавить version key для структуры localStorage, чтобы потом было проще делать migration.

# 15. Архитектура

Предпочтительно React + Vite + TypeScript.

Можно использовать:
- React;
- TypeScript;
- CSS Modules / Tailwind — выбрать один понятный подход;
- Framer Motion при необходимости;
- date-fns для дат;
- Lucide только для **обычных UI-иконок** типа play/pause/delete/settings.

### Важно про иконки

Lucide/иконки допустимы для функциональных мелких кнопок.

Они **НЕ заменяют**:
- котёнка;
- иллюстрации;
- декоративные арт-элементы;
- stage-up graphics.

Не использовать emoji в качестве UI icon system.

---

# 16. Доступность и UX

- корректные button elements;
- keyboard navigation;
- visible focus state;
- aria-label для icon-only buttons;
- достаточный contrast;
- не завязывать смысл только на цвет;
- модалки закрываются Escape;
- интерактивные элементы имеют hover/focus/active states.

---

# 17. Edge cases

Обработать:
- пустой список задач;
- длинный текст задачи;
- много задач;
- отсутствие тега;
- повторное открытие страницы при работающем timer;
- переход через полночь;
- завершение timer после возврата во вкладку;
- отсутствие audio file;
- повреждённые/старые localStorage данные;
- stage up при начислении сразу большого XP;
- максимальная стадия кота;
- click spam по complete/uncomplete.

При снятии отметки completed с задачи XP должен пересчитываться корректно и не позволять бесконечно фармить XP переключением checkbox.

Лучше считать pet XP детерминированно из истории завершённых задач + завершённых focus sessions или хранить award ledger/idempotent rewards.

# 19. Что должно происходить при первом запуске

1. Пользователь открывает сайт.
2. Видит красивый dashboard.
3. Появляется небольшой onboarding котёнка:
   - выбрать/ввести имя;
   - короткая фраза о том, что котёнок будет расти вместе с выполненными делами и focus-сессиями.
4. После подтверждения onboarding больше не мешает.
5. Можно сразу:
   - создать задачу;
   - выбрать тег;
   - включить brown noise;
   - запустить timer.
6. После первого завершённого дела котёнок красиво реагирует.
7. Progress visibly changes.

# 21. Визуальный quality gate

Перед тем как считать работу законченной, обязательно провести визуальную проверку.

Нужно открыть приложение и проверить минимум desktop + mobile.

Задать себе вопросы:

1. Выглядит ли первый экран как **реальный polished продукт**, а не tutorial project?
2. Котёнок сразу привлекает внимание?
3. Есть ли у страницы собственный характер?
4. Нет ли ощущения шаблона Tailwind / shadcn по умолчанию?
5. Не заменены ли иллюстрации эмодзи?
6. Хороша ли типографика?
7. Есть ли приятная визуальная иерархия?
8. Не перегружено ли всё одинаковыми карточками?
9. Все ли состояния hover/focus/active продуманы?
10. Красиво ли выглядит empty state?
11. Красиво ли выглядит страница с 10+ задачами?
12. Работает ли layout при узком экране?
13. Нет ли сломанных image assets?
14. Нет ли скачков размеров котёнка между стадиями?
15. Достаточно ли «вау», чтобы хотелось оставить вкладку открытой весь день?

Если ответы слабые — сделать второй визуальный проход.

**Не останавливаться после того, как “всё функционально работает”.**

# 25. Последнее важное указание

**Не выбирай самое быстрое и простое решение, если оно заметно ухудшает визуальный результат.**

Если выбор стоит между:

- «быстро поставить emoji-кота»  
и
- «потратить дополнительный шаг на генерацию согласованного character art»,

выбирай **character art**.

Если выбор стоит между:

- «оставить стандартный UI framework вид как есть»  
и
- «довести layout, typography, shadows, states и composition вручную»,

делай **второе**.

Этот проект должен быть не просто работающим. Он должен быть **таким красивым, чтобы пользователь хотел открыть его снова просто потому, что ему приятно на него смотреть**.
